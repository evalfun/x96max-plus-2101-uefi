# eMMC flash-in: layout, what was attempted, what is blocked

Goal: boot this firmware without any SD card, by making the box's eMMC boot
partition (`/dev/mmcblk2boot0`) carry our EDK2 as BL33.

Everything below was verified on the target hardware with a serial console
attached, with both boot partitions backed up first
(`/root/backup-20261113/boot{0,1}.img`). The BootROM's dual-copy fallback
works exactly as designed: whenever a modified boot0 failed, the box fell
back to the untouched boot1 and kept booting. No brick, ever.

## The boot partition layout (reverse-engineered)

4 MiB per copy. Structure (all offsets in the copy):

| Region | Offset | Content |
| --- | --- | --- |
| boot header | 0x0..0x200 | vendor ROM header (size/flags), keep as-is |
| BL2 | 0x200..0x10210 | signed BL2 (the `bl2.sig` produced by `aml_encrypt_g12a --bl2sig`) |
| FIP TOC | 0x10210 | magic `01 00 64 aa 78 56 34 12`, then 40-byte entries: uuid(16) + offset(8) + size(8) + flags(8) |
| BL30 | TOC+0x68000 | 0xe570 bytes (SCP firmware) |
| BL31 | TOC+0x76570 | 0x31600 bytes (ARM Trusted Firmware) |
| BL32 | TOC+0xa7b70 | size 0 in this box's table (unused placeholder) |
| BL33 | TOC+0xa7b70 | 0xae800 bytes — vendor U-Boot, LZ4-compressed |
| data end | ~0x166580 | everything after is zero |

The TOC uuids identify each blob (same list as
[`gxlimg`](https://github.com/repk/gxlimg): BL30
`9766fd3d-...`, BL31 `47d4086d-...`, BL33 `d6d0eea7-...`).

The boot log (`Load BL3X from eMMC, src: 0x00078200, size: 0x000ee400`) shows
BL2 loading BL30+BL31+BL33 as **one contiguous span** — and that span size
does *not* follow our edits to the TOC (see below), so it comes from
BL2-internal tables or the blob containers themselves.

## Attempt 1: replace the whole boot0 with our FIP

We build a complete FIP of our own (vendor BL2/BL30/BL31 inputs, our EDK2 as
BL33). The FD was shrunk from 4 MiB to 0xE0000 bytes (the actual FV content
is ~695 KiB; the rest was padding) so that `bl33.enc` + BL2 zone fits the
4 MiB partition with room to spare.

Result: **the BootROM rejected our BL2** before it printed anything —
`bl2.sig` produced with development keys does not pass the ROM's signature
check, and the box fell back to the untouched boot1. Replacing BL2 on this
box is therefore not possible without production keys. (A dev-fuse unit
would behave differently.)

## Attempt 2 (Plan B): keep vendor BL2/BL30/BL31 byte-identical, replace only BL33

Built an image identical to the vendor's except for:

* our BL33 payload written into the vendor's BL33 slot at `0xb7d80`,
* the TOC's BL33 size field updated (0xae800 → 0xe0400).

Result: BL2 ran (it is the vendor's own binary), loaded the **vendor-sized
span** (`size: 0x000ee400` — our TOC edit did not change it), truncated our
blob, and failed silently → boot1 fallback again.

Conclusion: the BL3X load size is not read from the TOC entry we edited; it
is fixed somewhere in BL2 (internal tables or container parsing against a
expected size). Making our 896 KiB EDK2 pass BL2's loader would require
reversing the exact source of that expectation and staying under it — and
the vendor BL2 may additionally verify BL33's container signature with the
production key, which we cannot satisfy.

## Where this leaves us

* **Supported install path:** SD-card gate (see README). Works, is
  reversible, and removing the card boots the stock chain.
* **eMMC BL33 replacement:** blocked by vendor BL2's blob loading; both
  "replace everything" and "replace only BL33" attempts are documented above.
* **Possible future paths**, in rough order of practicality:
  1. Replace the Android `boot.img` on the eMMC user area with a boot image
     whose "kernel" is our EDK2 (the vendor U-Boot loads and jumps it on
     every boot — no SD needed, no BL2 changes). Untested; needs the
     vendor boot.img format and an AVB check.
  2. Amend the vendor U-Boot environment on eMMC to run our gate from the
     eMMC user area instead of the SD card. Also untested.
  3. Reverse BL2's blob table (the `_DATA` blobs in the FIP header) well
     enough to forge a valid entry. Significant RE effort for one box.

## Artifacts & recipes used

```sh
# backup
ssh root@<box> 'dd if=/dev/mmcblk2boot0 of=/root/backup/boot0.img bs=1M'
# unlock (kernel marks boot partitions read-only)
echo 0 > /sys/block/mmcblk2boot0/force_ro
dd if=boot0-planb.img of=/dev/mmcblk2boot0 bs=1M conv=fsync
sync
echo 1 > /sys/block/mmcblk2boot0/force_ro
# read back and compare sha256 with the local image before rebooting
```

The images referenced here are not in the repository (they embed vendor
blobs); they are regenerated by `scripts/package-x96-fip.sh` from a build.
